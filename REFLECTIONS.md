### Reflection 3. Open-Meteo's air-quality numbers come from a reanalysis model, not a single physical sensor — meaning gaps are unlikely (the model backfills every hour). A raw sensor feed (say, a physical CO2 monitor bolted to a building) would behave completely differently. If your own run reports zero gaps, does that mean the gap-detection code in clean_series() is unnecessary and could be deleted? Argue your answer using the distinction between "this data source happened to be clean this one time" and "this data source is guaranteed to always be clean."
Non. Zéro trou sur une exécution montre seulement que la source était propre cette fois-ci, pas qu'elle le sera toujours : l'API peut tomber, changer de modèle ou renvoyer des valeurs nulles, et un capteur physique aura des pannes régulières. Le code de détection des trous ne coûte presque rien quand tout va bien, alors que sans lui un jour manquant passerait inaperçu dans la tendance et la projection.
### Reflection 4. Look at your own script output: the last 5 rolling-mean values versus the last 5 exponentially-smoothed values. They're close but not identical. In your own words, describe one real situation where you'd prefer the rolling mean over exponential smoothing, and one where you'd prefer the reverse — base this on how each one reacts to a sudden recent change versus a slow trend, not on the formulas themselves.
Je choisirais la moyenne glissante pour suivre une tendance lente comme l'évolution saisonnière du CO2 : elle donne le même poids à toute la semaine, donc un pic isolé ne la fait pas dévier. Je choisirais plutôt le lissage exponentiel quand il faut réagir vite à un changement brutal, comme une hausse soudaine de pollution près d'un site industriel : il donne plus de poids aux valeurs récentes et signale la rupture plus tôt, alors que la moyenne glissante met plusieurs jours à la montrer.
### Reflection 5. This pipeline has exactly one step that can fail unattended, at 6am on a Monday with nobody watching: the API call. fetch_hourly_co2's retry loop exists for that reason. What actually happens to data/series.csv and docs/data/series_analysis.json — do they go stale with last week's numbers, or does the dashboard break outright? Look at the workflow file and the scripts to answer, don't guess.
Les deux fichiers ne bougent pas et gardent les chiffres de la semaine précédente : le dashboard ne casse pas. Après le 4e échec, fetch_hourly_co2 lève une RuntimeError avant que fetch_series.py n'écrive quoi que ce soit, donc cette étape échoue et GitHub Actions saute les étapes suivantes. GitHub Pages continue alors d'afficher les anciennes données comme si de rien n'était : le seul signe de l'échec est la croix rouge dans l'onglet Actions.
